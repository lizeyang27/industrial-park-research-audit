# 用户可读报告

本参考规定审阅结果默认交给普通用户时的写法。读者不需要了解 Skill、评测分组或内部审计编码，也应能在第一次阅读后知道文章能否发布、为什么、先改什么，以及继续验证要付出什么成本。

## 固定结构

按照以下顺序输出；标题文字保持一致，便于不同运行结果对照。“结论”下的示例首句须按实际状态三选一，不能把三个选项一起留在报告中：

```markdown
# 审阅报告

## 结论
可以发布。
用两至四句话说明最主要理由、审阅范围和当前证据边界。

## 这篇文章已经做好的地方
- 保留两至四项真正影响判断或可读性的优点。

## 发布前需要处理
### 1. 用一句自然语言概括问题
- 原文位置：引用短语或说明段落位置，不粘贴大段原文。
- 为什么重要：说明它会怎样影响事实准确性、推理成立、读者决策或发布风险。
- 建议处理：给出补证、复算、缩窄、改成假设、删除或交人工判断的最小动作。

如果没有需要在发布前处理的事项，不使用三级标题，并把下面固定句作为独立完整行输出：

本稿没有仍需在发布前处理的问题。

## 建议怎么改
给出全篇层面的修改顺序；若用户没有要求整篇重写，不提供替代全文。

## 可继续研究的新观点
### 1. 用一句话写出新观点
- 适用对象：写明会采取行动或承担后果的参与方。
- 决策问题：写明这条观点会改变什么选择。
- 可能机制：写明新增变量、传导链或替代解释。
- 适用边界：写明地区、园区类型、产业、项目阶段、时间等范围。
- 反证条件：写明什么可观察结果会推翻或显著削弱观点。

给出零至两条原稿没有直接说出、且由产业机制与本次已准入证据共同支持的观点。每条至少需要一项明确绑定该观点且范围匹配的外部来源，或带同一观点外部血缘且已安全复算的派生结果；正文、公开/私有先验和知识卡不能单独支撑。证据不足时不使用三级标题，并把下面固定句作为独立完整行输出，不要凑数：

本稿暂不足以形成可靠的新观点。

## 如果还要继续核验
说明完成普通公开网页核验后仍可继续查什么，通常是付费、登录、私有、现场或专家资源；列出需要的来源、预计新增 token 区间、可能的外部调用次数和仍需哪类人工判断。给用户“停在当前结论”“只查选定问题”“再请行业专家判断”三个选择。

## 本次审阅没有验证什么
明确没有拿到或没有执行的来源核验、动态政策核验、现场经营数据、专家判断及其他限制。
```

“发布前需要处理”只展开最重要的零至八项。后台标为“发布前必须修改”或“阻断发布”的问题必须出现在这里；仅供参考的问题可以展示，对发布没有影响的问题不展示。若问题更多，合并同类项，并说明技术记录中还有明细；一个前台事项可以合并多个真正同类的后台问题，但技术记录必须解释合并理由。八项是前台展示上限，不是发现上限；默认公开完整模式必须另存未截断的技术台账。

零项时必须逐字使用“本稿没有仍需在发布前处理的问题。”，且不得同时写三级标题。该句必须是独立完整行；两个零项固定句作为否定、引语或长句子串出现均不计入。零项不代表技术台账为空：已经关闭、只作参考或对发布没有影响的技术记录仍可保留。

## 可读性不变量

- 主报告只使用“可以发布”“修改后发布”“暂缓发布”表达结论；不出现英文工作流状态。
- “结论”标题后的第一个非空句必须是三种完整首句之一：“可以发布。”“修改后发布。”“暂缓发布。”也接受中文/英文感叹号或英文句点作句末符号。不要在规范结论前增加否定词、引号、条件句或“尚不能说”等前缀。
- 主报告不展示内部风险、验证、可发现性、发现通道、关闭路线或粒度编码，也不展示主张 ID、问题 ID、知识卡 ID、框架节点 ID 和机器字段名。
- 用“会影响核心结论”“重要但可修正”“属于优化建议”等自然语言表达后果；用“可直接复算”“需要查当前政策或原始来源”“需要行业专家判断”表达验证难度。
- 每个问题使用一个三级标题，并同时保留“原文位置”“为什么重要”“建议处理”三条标签。标题中的问题短语应具体；三条标签的值都必须至少包含四个实质性的非空白字符，其中用于和后台交叉绑定的逐字短语也至少包含四个非空白字符，且前台出现处不能被有限词表中的明显否定前缀直接否定。只有风险标签、只有一句“建议补数据”或只有搜索方向，都不算可执行建议。
- 每条新观点使用一个三级标题，并逐条保留“适用对象”“决策问题”“可能机制”“适用边界”“反证条件”五个标签；五个值都必须是至少四个非空白字符的实质说明。后台相应字段的完整文字必须逐字、且不被明显否定地出现在对应标签值中；完整“可能机制”后台字段不能逐字复制草稿。不能只靠标题哈希把不同意思的两层文字绑在一起，也不能把原稿原句换一个标签就称作新观点。
- 区分“原文称”“现有材料支持”“本次据此推断”“仍待核验”。证据缺失不等于事实为假。
- 若已联网，在相关问题中用普通语言交代“已核实”“仅部分支持”“来源相互冲突”或“仍未找到原始依据”，并把网址、定位、适用范围和核验日期保留在单独技术台账；搜索摘要不能写成已经证实。
- 先合并重复问题，再按对核心命题和发布决定的影响排序。表达和排版建议不能盖过事实、比较、因果、政策适用或声誉问题。
- 若没有拿到原始来源或没有联网，不用肯定语气宣布外部事实错误；说明当前只能识别证据缺口或内部矛盾。
- token 只报规划区间及估算假设，不冒充实际消耗、金额报价或模型价格。
- 七个固定二级标题各出现一次且顺序不变，每节都必须有实质正文；零问题与零观点分别用规定固定句满足正文要求。三级标题只能出现在“发布前需要处理”和“可继续研究的新观点”两节，普通章节不得用三级标题伪装额外事项。主报告层不能使用 HTML 注释或围栏代码块隐藏内容；如需技术字段，只能放到下述精确的技术附录标题之后。

校验器会在“可以发布”后查找一组常见的“不得发布、暂缓、撤回”等冲突表述，以挡住明显自相矛盾；它也会对四个问题摘录和五个观点字段做有限的明显否定前缀检查，并拒绝观点机制逐字复制草稿。这些都只是保守的机械词面边界，不证明整份结论语义一致、前后台语义等价或观点真正新颖。

## 私有经验与阅读框架如何披露

私有经验可以改变“先问什么”和“怎样组织问题”，但不会自动成为目标文章的事实证据。若它实际参与本次发现，在主报告中用一至三句话说明：

1. 它提示了哪类边界、参与方、机制或反例问题；
2. 它是问题线索、来源追溯、阅读框架还是已经准入的独立证据；
3. 哪些目标事实仍需原始来源、当前政策或专家独立验证。

不要在主报告写出私有文件名、人员、路径、内部编号、原文批注或可反推雇主身份的信息。需要证明知识在读稿前参与时，把时间、授权、哈希、先验问题引用、支持项引用和框架节点引用放进单独技术记录。

## 对照运行

A/B/C/D/E/F 必须使用完全相同的固定结构、结论词和问题上限。组别名称可以出现在报告标题或单独评测说明中，但不能用来代替对读者有意义的判断。比较报告应另外说明各组允许读取的输入、私有信息是否实际被使用、增加了什么问题或改变了什么排序，以及哪些差异仍可能来自单次模型波动。

若正文在框架冻结前已被任何参与生成框架的上下文看到，必须把该案例标为回溯演示；不得声称它证明了严格的读稿前因果效果。

## 技术附录边界

默认把完整技术台账保存为另一份文件，并与草稿和主报告做哈希绑定。用户明确要求把技术信息放在同一文件时，只能置于一行完全匹配的 `## 技术附录` 标题之后；主报告部分仍须满足全部可读性不变量。除非用户明确选择快速或纯文字模式，不能因为前台报告最多八项就丢弃后台问题。

保存 Markdown 后、交付前运行 `python scripts/validate_user_report.py <report.md>`。该脚本只检查标题结构、各节实质正文、三级标题位置、首句格式、问题与观点数量、固定零项句、五个新观点标签、常见明显冲突词和内部字段隔离。完整 bundle 校验器还用技术台账中的前台序号与四个逐字摘录绑定问题，并要求每条新观点的五个后台字段逐字出现在对应前台标签值中；这种字节与子串关系仍不证明两层文本语义等价，也不证明审阅判断正确。
