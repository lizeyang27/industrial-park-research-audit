# 用户可读报告

本参考规定审阅结果默认交给普通用户时的写法。读者不需要了解 Skill、评测分组或内部审计编码，也应能在第一次阅读后知道文章能否发布、为什么、先改什么，以及继续验证要付出什么成本。

## 固定结构

按照以下顺序输出；标题文字保持一致，便于不同运行结果对照：

```markdown
# 审阅报告

## 结论
可以发布 / 修改后发布 / 暂缓发布。
用两至四句话说明最主要理由、审阅范围和当前证据边界。

## 这篇文章已经做好的地方
- 保留两至四项真正影响判断或可读性的优点。

## 发布前需要处理
### 1. 用一句自然语言概括问题
- 原文位置：引用短语或说明段落位置，不粘贴大段原文。
- 为什么重要：说明它会怎样影响事实准确性、推理成立、读者决策或发布风险。
- 建议处理：给出补证、复算、缩窄、改成假设、删除或交人工判断的最小动作。

## 建议怎么改
给出全篇层面的修改顺序；若用户没有要求整篇重写，不提供替代全文。

## 如果还要继续核验
分别说明可以继续查什么、需要哪类来源、预计新增 token 区间、可能的外部检索次数和仍需哪类人工判断。给用户“停在当前结论”“只查选定问题”“再请行业专家判断”三个选择。

## 本次审阅没有验证什么
明确没有拿到或没有执行的来源核验、动态政策核验、现场经营数据、专家判断及其他限制。
```

“发布前需要处理”只展开最重要的零至八项。若问题更多，合并同类项，并说明技术记录中还有明细；不要用长表格淹没优先级。

## 可读性不变量

- 主报告只使用“可以发布”“修改后发布”“暂缓发布”表达结论；不出现英文工作流状态。
- 主报告不展示内部风险、验证、可发现性、发现通道、关闭路线或粒度编码，也不展示主张 ID、问题 ID、知识卡 ID、框架节点 ID 和机器字段名。
- 用“会影响核心结论”“重要但可修正”“属于优化建议”等自然语言表达后果；用“可直接复算”“需要查当前政策或原始来源”“需要行业专家判断”表达验证难度。
- 每个问题同时回答“在哪里”“为什么重要”“最小怎么改”。只有风险标签、只有一句“建议补数据”或只有搜索方向，都不算可执行建议。
- 区分“原文称”“现有材料支持”“本次据此推断”“仍待核验”。证据缺失不等于事实为假。
- 先合并重复问题，再按对核心命题和发布决定的影响排序。表达和排版建议不能盖过事实、比较、因果、政策适用或声誉问题。
- 若没有拿到原始来源或没有联网，不用肯定语气宣布外部事实错误；说明当前只能识别证据缺口或内部矛盾。
- token 只报规划区间及估算假设，不冒充实际消耗、金额报价或模型价格。

## 私有经验与阅读框架如何披露

私有经验可以改变“先问什么”和“怎样组织问题”，但不会自动成为目标文章的事实证据。若它实际参与本次发现，在主报告中用一至三句话说明：

1. 它提示了哪类边界、参与方、机制或反例问题；
2. 它是问题线索、来源追溯、阅读框架还是已经准入的独立证据；
3. 哪些目标事实仍需原始来源、当前政策或专家独立验证。

不要在主报告写出私有文件名、人员、路径、内部编号、原文批注或可反推雇主身份的信息。需要证明知识在读稿前参与时，把时间、授权、哈希、先验问题引用、支持项引用和框架节点引用放进单独技术记录。

## 对照运行

A/B/C/D/E/F 必须使用完全相同的固定结构、结论词和问题上限。组别名称可以出现在报告标题或单独评测说明中，但不能用来代替对读者有意义的判断。比较报告应另外说明各组允许读取的输入、私有信息是否实际被使用、增加了什么问题或改变了什么排序，以及哪些差异仍可能来自单次模型波动。

若正文在框架冻结前已被任何参与生成框架的上下文看到，必须把该案例标为回溯演示；不得声称它证明了严格的读稿前因果效果。

## 技术附录边界

默认把技术台账保存为另一份文件。用户明确要求把技术信息放在同一文件时，只能置于独立的 `## 技术附录` 标题之后；主报告部分仍须满足全部可读性不变量。

保存 Markdown 后、交付前运行 `python scripts/validate_user_report.py <report.md>`。校验器只证明标题结构、问题数量和内部字段隔离符合本契约，不证明审阅判断正确。
