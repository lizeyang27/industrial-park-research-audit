# 推理审计

本参考用于审查产业研究稿中的主张是否被证据支持、推理是否成立，以及哪些问题必须交由人工判断。它不负责替作者选择研究立场，也不负责从传播稿重构投资命题；需要重构命题时，先阅读 `thesis-reconstruction.md`，再用本参考逐项审计重构结果。

## 审计原则

- 把“原文写了什么”“证据能证明什么”和“作者据此推断什么”分开记录。
- 异常是复核线索，不等同于事实错误；未经人工确认，不输出“造假”“误导”等定性判断。
- 证据缺失时降低结论强度或标记待核验，不补写不存在的来源。
- 事实、计算结果、推断、预测、价值判断和行动建议使用不同标签。
- 保留原意优先。只有用户要求改写时才提供修订稿；默认先给审计意见。

## 原子主张拆解

将一句话拆成可单独验证的最小主张。每个原子主张只保留一个主体、一个谓词、一个对象和必要限定条件。

为每项主张记录：

- `claim_id`：稳定标识符。
- `claim_text`：不改变含义的简短转述。
- `claim_type`：事实、计算、推断、预测、判断或建议。
- `subject`：主张针对的企业、行业、产品、区域或政策对象。
- `scope`：样本、地域、时间、产品类别和统计口径。
- `qualifier`：可能、通常、部分、整体、必然等强度词。
- `source_anchor`：原文段落、表格、图注或批注位置。

一句话同时包含事实和结论时必须拆开。例如，“指标下降，因此竞争力恶化”至少包含一个可观察事实和一个解释性推断，不能共用同一核验状态。

## 隐含前提

对每个推断或建议追问：若结论成立，还必须有哪些未写出的条件？重点识别：

- 指标能够代表所声称的经营或行业状态。
- 样本能够代表目标总体。
- 不同来源采用相同定义、时点和统计口径。
- 比较对象除研究变量外不存在决定性差异。
- 观察到的变化并非由宏观环境、会计口径、产品结构或一次性事件造成。
- 某项政策在目标时间和地区确实适用。
- 作者描述的行为动机能由公开证据证明，而不只是推测。

将前提标记为“已证实”“部分支持”“未验证”或“与证据冲突”。前提未验证时，结论不能获得高于前提的可信等级。

## 证据审查

为主张建立证据链，而不是只登记链接。检查：

- **来源层级**：优先原始公告、监管或政府文件、正式财务披露、技术标准和可追溯数据库；二手报道用于补充语境，不替代关键原始来源。
- **直接程度**：区分来源直接披露、根据披露计算、跨来源拼接和作者判断。
- **适配程度**：来源是否真的覆盖该主体、期间、地区、技术路线和产品类别。
- **时效性**：动态数据和政策结论必须带核验时点；历史材料不能自动代表当前状态。
- **完整性**：是否只选取支持结论的片段，遗漏定义、限制条件或相反数据。
- **可复算性**：派生数字保留公式、单位、分母、舍入方式和原始值。

推荐状态：`supported`、`partially_supported`、`derived`、`contradicted`、`conflicting`、`stale`、`missing`、`not_verifiable`。不得把网页存在等同于主张成立。

## 因果审计

出现“导致”“因此”“取决于”“倒逼”“决定”等语言时，执行以下检查：

- 先确认时间顺序，原因应先于结果。
- 说明可能机制：该因素通过什么中间环节影响结果。
- 列出至少一种合理的替代解释，并检查是否有证据排除。
- 区分个案解释、样本相关关系和行业普遍规律。
- 检查是否存在共同原因、反向因果、选择偏差或幸存者偏差。
- 多因素共同作用时，避免把结果归因于单一变量。

若证据只能支持相关性，将因果句改为并列事实、相关关系或待验证假设。不得仅靠语气变弱来掩盖仍然断裂的推理链。

## 比较审计

任何横向或纵向比较都应明确：

- 比较目的和待解释差异。
- 主体、期间、币种、单位、样本范围和计算方法是否一致。
- 产品结构、生命周期、政策环境和资产组合是否具有可比性。
- 基准是否经过有利选择，是否遗漏更合适的对照组。
- 差异是否超过正常波动，并具有业务意义。

若可比性不足，删除强行比较，或明确写成“仅作背景、不用于因果判断”。同一主体或同一时间并不自动构成有效对照。

## 反证与替代解释

对核心结论主动寻找会使其失效的证据：

- 哪种新事实会推翻或显著削弱结论？
- 是否存在表现相反但条件相似的案例？
- 改变样本边界、时间窗口或指标定义后，结论是否仍成立？
- 若关键变量没有变化，结果是否仍可能发生？
- 作者最不愿看到但必须披露的证据是什么？

无法找到反证不代表命题为真。若稿件未讨论明显替代解释，应将其列入人工复核队列。

## 风险与验证路由

按“如果不修正会造成什么后果”分级，而不是按措辞是否刺眼分级：

- `R3`：核心事实、术语、数字、因果、政策适用或高风险指控缺乏支持；关闭前暂缓发布。
- `R2`：范围外推、比较不可比、关键前提未验证、重要反证遗漏，可能显著改变读者判断。
- `R1`：局部语气、清晰度或结构问题，不改变主要事实和决策。

另按关闭问题所需证据标注验证难度：`V1` 为正文与直接来源的显性核验，`V2` 为受众、利益相关方和政策语境核验，`V3` 为行业机制与专家判断。难度与风险不可互相推导，具体规则见 `verification-routing.md`。

风格问题不得自动升级为事实错误；出现敏感关键词也不得自动判定违规。

## 人工关闭

每个问题都必须保留关闭状态和证据，建议字段如下：

- `issue_id`
- `claim_id`
- `category`
- `risk_level`
- `verification_level`
- `level_basis`
- `problem`
- `reason`
- `required_evidence`
- `suggested_action`
- `owner`
- `status`：待处理、已修改、已补证、接受风险、误报或无法核验。
- `closure_note`
- `closure_evidence`
- `reviewed_by`
- `reviewed_at`

只有人工复核者可以将问题设为关闭。文本已修改不等于问题已解决；应重新检查修改后的主张、来源和上下文。`R3` 未关闭时，结论只能是“暂缓发布”。自动化可以生成问题和候选修订，但不得代替关闭签字。

## 建议输出

先给简短结论，再给问题台账：

| 字段 | 内容 |
|---|---|
| 发布建议 | 可发布、修改后发布或暂缓发布 |
| 原子主张 | 被审查的最小主张 |
| 风险级与验证级 | 为什么需要处理、关闭问题需要哪类证据 |
| 证据状态 | 已支持、部分支持、冲突或待核验 |
| 推理缺口 | 隐含前提、因果或比较问题 |
| 建议动作 | 补证、缩窄范围、改为假设、删除或交人工判断 |
| 关闭条件 | 什么证据或修改足以关闭问题 |

最后单列尚未关闭的 `R3` 和 `R2`，避免它们被风格建议淹没，并给出继续 `V2`、`V3` 核验的增量 token 规划区间。
